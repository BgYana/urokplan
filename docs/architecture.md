# Архитектура серверной части

## Общая схема

Сервер реализуется как модульный монолит. Один процесс и одна PostgreSQL обслуживают несколько предметных модулей, но каждый модуль владеет своими таблицами, миграциями и репозиториями.

`server/app` является точкой сборки приложения: загружает конфигурацию, запускает общую инфраструктуру и подключает публичные API предметных модулей. Бизнес-правила в этом модуле не размещаются.

`platform/database` содержит только HikariCP, запуск Liquibase, подключение Exposed и границу транзакции. Он не содержит предметных таблиц.

Предметные модули добавляются вместе с работающими сценариями:

- `identity` — аккаунты, роли и сессии;
- `relationships` — учебные и родительские связи;
- `courses` — курсы, группы, участие и цены;
- `scheduling` — занятия, серии и посещаемость;
- `billing` — платежи, единицы оплаты, начисления и списания;
- `learning` — домашние задания без файлов, оценки и обратная связь.

## Зависимости

- `server/app` зависит от публичных API предметных модулей и собирает приложение.
- Предметный модуль может использовать общую транзакционную инфраструктуру.
- Межмодульный вызов выполняется через публичный Kotlin-интерфейс, а не через чужой репозиторий.
- Модуль не читает и не изменяет таблицы другого модуля напрямую.
- HTTP DTO, бизнес-модели и модели хранения разделяются.

Каждый предметный модуль разделяется на пакеты `domain`, `application`, `infrastructure` и `http`. HTTP-маршруты зависят только от интерфейсов сценариев application-слоя. Прикладные сервисы зависят от портов репозиториев и `TransactionRunner`, но не от Ktor, Exposed или HikariCP. Внутренние реализации соединяет фабрика модуля, а `server/app` выступает общим composition root.

Если одному сценарию нужны изменения нескольких модулей, прикладной сервис задаёт одну транзакционную границу и вызывает их публичные интерфейсы. Направление зависимости фиксируется в Gradle и не образует циклов.

## Данные и миграции

Liquibase — единственный механизм изменения схемы. Корневой YAML-changelog задаёт порядок модулей, а предметные changeset пишутся на Liquibase formatted SQL и принадлежат своим модулям. Exposed используется только для типобезопасных запросов и не создаёт таблицы автоматически.

Для локальной разработки PostgreSQL и сервер запускаются через Docker Compose. Параметры подключения поступают из переменных окружения. Интеграционные тесты поднимают настоящую PostgreSQL через Testcontainers.

## Границы первой лабораторной

Реализуются аккаунты, связи, курсы, группы, расписание, оплата через mock-провайдер, домашние задания без вложений, оценки и обратная связь. Файловые вложения и уведомления не входят в лабораторную. Материалы и объявления не входят в продукт.

Приложение не реализует видеозвонки. В курсе, группе или занятии хранится обычная ссылка на внешний сервис связи.
